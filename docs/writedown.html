Writedown

Write the program and what it outputs together, top to bottom, with rules strict enough that you have to think like a compiler.

Why Quick tour Example Rules Grammar

Why Writedown

  • Rigid rules. You have to think the way a compiler does.
  • Top to bottom. You never go back to edit what you've already written.
  • Works on paper. It's as easy to write by hand as it is to type.
  • Repetitive on purpose. Output repeats in a fixed shape, so patterns are easy to spot.

If it works, it could also be:

  • an export format for logs
  • a way to test code automatically, by diffing two Writedown files of the same run
  • a way to teach intro CS to almost anyone, without a computer

There is no loop keyword. To loop, write a function that calls itself.

Example: doubling four times

The algorithm:

  1. Set loop to 0 and doubler to 1
  2. Add 1 to loop
  3. Multiply doubler by 2
  4. If loop < 4, go to step 2
  5. Return doubler

In Writedown, the code comes first. Then the call, and its output block traces every step.

Rules

  • All variables are functions. A variable behaves like a function with no arguments that returns its current value. That's why its output is written the same way as any other output.
  • Every function gives output, even when piped.
  • Inside a function block or an argument (<>) block, you don't have to write outputs.
  • Deferred output goes in an o block and is written as variable[output] or ?[output].
  • Outside <>, each output line shows one variable.
  • To change a function, rewrite it from scratch, or pipe it to add the changes.
  • Variable names can't start with c, because that prefix is reserved for constants.
  • A variable can't be named t, f or o, because those lines are block words.

Formal grammar

Writedown is read one line at a time. Each line holds at most one statement, and can end with a comment.

This is written in EBNF: = defines a rule, | means "or", [ ] means optional, { } means zero or more, and quoted text is written literally.

program      = { line } ;
line         = [ statement ] [ comment ] NEWLINE ;
comment      = "#" { any-char } ;

statement    = block-word | fn-start | fn-end | if-head
             | return | call | const-decl | assignment | update
             | trace-list ;

(* blocks *)
block-word   = "t" | "et" | "f" | "ef" | "o" | "eo" ;
fn-start     = "f" name [ "<" params ">" ] ;
fn-end       = "e" name ;
params       = name { "," name } ;
if-head      = expr "?" ;

(* actions *)
return       = "r" "<" args ">" ;
call         = "=" name "<" [ args ] ">" ;
args         = arg { "," arg } ;
arg          = trace | expr ;
const-decl   = const-name "=" expr ;
assignment   = var-name "=" expr ;
update       = var-name ( "++" | "--" | assign-op expr ) ;
assign-op    = "+=" | "-=" | "*=" | "/=" ;

(* outputs *)
trace-list   = trace { "," trace } ;
trace        = var-name   "["  value "]"
             | const-name "[[" value "]]"
             | "?" "[" ( "true" | "false" ) "]"
             | "<" trace { "," trace } ">" ;
value        = expr ;

(* expressions *)
expr         = sum [ compare-op sum ] ;
compare-op   = "<" | ">" | "<=" | ">=" | "==" | "!=" ;
sum          = term { ( "+" | "-" ) term } ;
term         = factor { ( "*" | "/" | "%" ) factor } ;
factor       = number | string | "true" | "false"
             | var-name | const-name | call | "(" expr ")" ;

(* words *)
name         = letter { letter | digit | "_" } ;
const-name   = "c" name ;
var-name     = name ;      (* must not start with "c" *)
number       = [ "-" ] digit { digit } [ "." digit { digit } ] ;
string       = '"' { char | "{" name "}" } '"' ;

Reading a line

Some lines look alike, so a reader decides what a line is by checking in this order:

  1. The whole line is t, et, f, ef, o or eo: it's a block word.
  2. The line ends with ?: it's an if head, and every < or > on it is a comparison.
  3. The line is f followed by a name and maybe <params>: it starts a function.
  4. The line is e followed by a name and nothing else: it ends a function.
  5. Anything else is matched against the remaining statement rules.

Rules the grammar can't check

These need a checker that reads the whole file, not just one line:

  • every fname has a matching ename later on
  • every t is closed by et, every f by ef, and every o by eo
  • t and f blocks only come right after an if head
  • an o block comes right after the call whose output it shows
  • outside a function or <> block, every statement gives an output
  • outside <>, each output line shows one variable
